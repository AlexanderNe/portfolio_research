## 2. Часть A. Research (Python)

### 2.1 🔴 A1 (Blocker). Повторный вход на том же баре по цене его открытия

**Файл:** `strategy_research.py:170–304` (цикл `Simulator.run`), критично — `strategy_research.py:247–254`.

Внутри одной итерации по бару `i` код сначала закрывает позицию, а затем **сразу же открывает новую по цене `op` — открытию того же бара `i`**:

```python
# --- manage open position on this bar ---
if position is not None:
    ...
    if lo <= position["sl"]:
        exit_price, reason = position["sl"], "stop_loss"   # выход внутри дня i
    ...
    position = None

# --- entry on prior bar's signal ---
if (position is None and i > 0 and signals[i - 1] != 0 ...):
    ...
    entry = op          # ← цена ОТКРЫТИЯ того же бара i
```

Физически это невозможно: на открытии бара `i` позиция ещё была открыта, стоп сработал позже внутри дня, и купить/продать по утреннему открытию задним числом нельзя. Это не «заглядывание в будущее» в сигнале (сигнал берётся с `i−1` корректно) — это **машина времени в исполнении**.

**Измеренный масштаб** (walk-forward 504/126, риск 10%, комиссия 0,04%, без плеча):

| Проверка | Значение |
|---|---|
| Доля таких входов (SBER, GAZP, LKOH) | **438 из 633 = 69,2% всех сделок** |
| Их доля в PnL | **+482 648 ₽ из +624 008 ₽ = 77,3%** |

Сравнение трёх моделей исполнения на 8 бумагах (SBER, GAZP, LKOH, ROSN, NLMK, CHMF, TATN, ALRS), пул 800 тыс. ₽, ~9,5 лет OOS:

| Модель | Итог PnL | Сделок | % к пулу |
|---|---|---|---|
| **Как сейчас** (вход по открытию текущего бара) | **+1 803 031 ₽** | 1 650 | +225,4% |
| Вход на том же баре, но **по цене выхода** (максимально щедрая реалистичная версия) | +792 134 ₽ | — | −56,1% к базе |
| **Вход только со следующего бара** (по правилу стратегии) | **+339 864 ₽** | 1 343 | +42,5% |
| То же + прогретый ATR (фикс A6) | +339 864 ₽ / **+42,5%** | — | 3 бумаги из 8 уходят в минус |

Обратите внимание: при корректной модели **количество сделок падает всего на 19%** (1 650 → 1 343) — сигнал никуда не девается, вход просто сдвигается на следующий бар. А PnL падает на **81%**. Значит, преимущество давал не сигнал ROC, а благоприятная цена входа задним числом.

По 8 бумагам: GAZP, ROSN, TATN становятся убыточными. Тезис «40/40 бумаг прибыльны» с высокой вероятностью не переживёт пересчёта.

**Что чинить:**

```python
for i in range(n_bars):
    exited_this_bar = False
    ...
    if exit_price is not None:
        ...
        position = None
        exited_this_bar = True
    ...
    if (position is None and not exited_this_bar and i > 0 and signals[i-1] != 0 ...):
```

Это ровно правило, описанное в `TECHNICAL.md` §3 («вход по открытию следующего бара, максимум одна позиция на бумагу»). Текущий код это правило нарушает — он позволяет двум позициям занимать одно и то же открытие.

> После фикса нужно **перегенерировать весь `report/`** (кэш обязательно удалить) и переписать заголовочные цифры в `README.md` и `TECHNICAL.md`. Если после этого стратегия окажется убыточной — это и есть честный ответ исследования.

### 2.2 🟠 A2. Просадка пула считается только по реализованному PnL

**Файл:** `report_build.py:104–117` (`pool_metrics`), `report_build.py:188–195` (`chart_pooled`).

```python
for _, tr in trades.iterrows():
    d = pd.Timestamp(tr["exit_time"]).normalize()
    eq[d] = eq.get(d, 0) + tr["pnl"]
ser = pd.Series(eq).sort_index()
eqv = pool + ser.cumsum()
pool_dd = float((eqv / eqv.cummax() - 1).min() * 100)
```

Кривая строится **только по датам выходов** и **только по закрытым сделкам**. Открытые позиции (средний срок удержания 16,2 дня) в переоценку не входят вовсе. Это систематически занижает просадку: реальный счёт видит «бумажный» минус каждый день, а не только в день фиксации.

**Измерено** на тех же 8 бумагах (пул 800 тыс. ₽, 1 650 сделок):

| Метод | maxDD пула |
|---|---|
| Как в отчёте (только реализованный PnL) | **−14,05%** |
| Mark-to-market (открытые позиции по дневному закрытию) | **−18,11%** |

Занижение ~29% относительных. Для заявленной цифры **−9,3%** это означает реальную величину порядка −12%…−13% (диверсификация 40 имён сгладит, но направление ошибки то же).

Отдельно: методика непоследовательна внутри самого пакета — `chart_signals()` (`report_build.py:341–355`) для **одной бумаги** честно строит mark-to-market кривую, а сводная кривая пула — нет.

**Чинить:** считать пул так же, как `chart_signals`: `POOL*N + cumsum(realized) + Σ unrealized(открытые позиции по close дня)` на полном торговом календаре.

### 2.4 🟠 A4. Дивидендные гэпы не моделируются — а они «кормят» шорты

Данные MOEX ISS — **цены без корректировки на дивиденды**. Значит:

* **Лонг**, удерживаемый через отсечку, видит гэп вниз на размер дивиденда и фиксирует убыток (иногда — стоп). В реальности трейдер получает дивиденд и компенсирует гэп. Бэктест **занижает лонги**.
* **Шорт** через ту же отсечку получает гэп в свою пользу как чистую прибыль. В реальности при шорте акции дивиденд списывается в пользу кредитора, а при шорте **фьючерсом** (заявленный способ исполнения, `report/report.md` §9 п.5) гэпа просто нет — дивиденд уже в базисе. Бэктест **завышает шорты**.

Грубая оценка порядка (средний срок удержания 16,2 календарных дня, ~1,3 отсечки на имя в год, типичная разовая доходность 5–7%, номинал позиции ≈ 100 тыс. ₽): ~5–6% из 7 192 сделок пересекают отсечку → **~2,0–2,5 млн ₽ направленного эффекта** при итоге 8,04 млн ₽. Он частично сокращается между сторонами, но:

* вывод «шорты дают 53% прибыли и PF 1,41» (`report/tables/long_short_split.csv`) держится на не смоделированном эффекте;
* вывод «обе стороны самодостаточно прибыльны» нужно перепроверять на скорректированных на дивиденды сериях.

**Чинить:** либо загружать total-return серию / список отсечек и корректировать PnL (лонг +div, шорт −div), либо явно исключать из выборки сделки, пересекающие отсечку, и показывать обе версии. В `report/report.md` §9 дивиденды не упомянуты вообще — это серьёзный пробел в списке оговорок.

### 2.5 🟡 A5–A9. Методические дефекты среднего уровня

**A5. Знаменатель лет.** `report_build.py:1306`:

```python
years = (nbits - 504 - 126) / 252.0
```

`nbits` = максимум баров по всем именам = 2 920 (HYDR/MOEX/PIKK/SNGS с 2015-01-16). Формула даёт 9,087 года. Фактическое OOS-покрытие: `floor((2920−504)/126) = 19` фолдов × 126 = 2 394 бара = **9,50 года**. Лишнее вычитание `oos_days` выбрасывает последний фолд из знаменателя.

Итог: **22,13%/год завышено до ~21,2%/год** (+4,5% относительных). Формула должна быть `folds * oos_days / 252`.

Отдельно: `per_year = total / pool * 100 / years` — это **простая** среднегодовая, а не CAGR. При фиксированном пуле (прибыль не реинвестируется) это корректно, но в графике `returns_by_year.png` она сравнивается с годовыми доходностями IMOEX, которые по природе составные. В подписи стоит явно указать «простая, прибыль выводится».

**A6. ATR не прогревается на границе фолда.** `strategy_research.py:949–952` аккуратно прогревает **сигнал**:

```python
warm = min(WARMUP, len(train))
oos_sig = STRAT_FUNCS[name](pd.concat([train.tail(warm), oos], ignore_index=True), params)
```

но `Simulator` для OOS создаётся на голом `oos` (строка 953) и считает `compute_atr(oos, 14)` с нуля: первый ATR = `high−low` первого бара, дальше EWM сходится ~40 баров. Это **первые ~30% фолда из 126 баров** с искажённым ATR, который определяет и размер позиции, и дистанцию стопа.

Измеренный вклад невелик (−80,9% против −81,2% в комбинации с A1), но исправляется тремя строками: считать ATR на `concat(train.tail(warm), oos)` и передать срез `[warm:]` в `Simulator`.

**A7. Выход «по концу фолда».** Каждый фолд обрывает открытую позицию по `close` последнего бара с `reason="backtest_end"`. Это ровно 1 сделка на фолд на бумагу: 18 из 213 сделок SBER = **8,5% сделок и 7,3% PnL**. Реальный счёт не флэтится каждые полгода. Правильно — переносить позицию и её cash между соседними фолдами (менять только параметры), иначе walk-forward измеряет ещё и артефакт нарезки.

Там же: каждый фолд стартует со свежих `DEFAULT_INITIAL_CAPITAL = 100_000` — это заявленный «фиксированный пул», но стоит документировать явно, что cash тоже сбрасывается (реализованный PnL не переносится, значит размер позиции не растёт и не падает).

**A8. Отбор параметров без издержек.** `report_build.cfg()` задаёт `"fee_selection": False`, поэтому в `walk_forward` (`strategy_research.py:916–917`) кандидаты отбираются с **нулевой комиссией**, а применяются с 0,04%. Для стратегии с ~1,6 сделки на бумагу в месяц это не смертельно, но систематически сдвигает выбор в сторону более частых параметров. Разумнее по умолчанию `fee_selection=True`.

Критерий отбора — `sharpe`, посчитанный как `daily_close.pct_change()` по equity (`strategy_research.py:378–383`). Equity включает нереализованную переоценку и при шорте может резко менять знак вклада; `pct_change` по такой серии не является доходностью портфеля в общепринятом смысле. Плюс нет тай-брейка (при равном Sharpe побеждает первый в порядке перебора) и нет штрафа за число сделок. Минимальный улучшенный вариант — отбор по медиане/Sharpe **с** издержками и тай-брейк по числу сделок.

**A9. Лотность, проскальзывание, гэпы.** `units` считается в **штуках**, тогда как MOEX торгует лотами (SBER — 10, VTBR — 10 000, GAZP — 10). `int(...)` вниз частично маскирует, но фактический размер позиции округляется к лоту, и для дорогих лотов расхождение достигает единиц процентов номинала. Проскальзывание не заложено вовсе, выход всегда происходит **ровно по уровню** SL/TP даже если бар открылся сквозь него гэпом (`strategy_research.py:208–218`). В `report.md` §9 гэпы упомянуты, но эффект не оценён; для стратегии, где ~47% выходов — стопы, это важно. Минимум: выход по `min(open, sl)` для лонга, `max(open, sl)` для шорта.

### 3.1 🔴 B1 (Blocker). Вход по цене утреннего открытия спустя часы после открытия

**Файл:** `PortfolioTradingSystem.Application/Engine/InstrumentEngine.cs:316, 346–348`.

```csharp
bool positionExistedBeforeThisCandle = _state.Position is not null;
...
if (!positionExistedBeforeThisCandle && !_enteredThisSession && _sessionBar is { } bar)
{
    var opened = _state.TryOpen(bar.Open, minute.Time);   // bar.Open — открытие СЕССИИ
```

Сценарий: позиция открыта вчера, сегодня в 11:40 срабатывает стоп. На следующей минутной свече `positionExistedBeforeThisCandle == false`, `_enteredThisSession == false` (вход был не сегодня) → движок открывает новую позицию **по `_sessionBar.Open`, то есть по цене 10:00**.

Последствия хуже, чем в бэктесте:

* в Telegram уходит `OPEN LONG SBER / entry: <цена 10:00>` в 11:41 — исполнить её нельзя;
* `StopLoss` и `TakeProfit` считаются от этой недостижимой цены (`MomentumEngineState.cs:160–170`), то есть оператор получает **неверные уровни**;
* внутренний учёт cash/equity расходится с любым реальным исполнением с первой же такой сделки.

Дополнительно: после старта/`Resume` в середине дня `_sessionBar` инициализируется **первой полученной минуткой** (`InstrumentEngine.cs:325–329`), поэтому «открытие сессии» — это цена момента запуска. Это описано в `AGENTS.md` как известное поведение, но в связке с повторным входом оно превращается в «цена входа = цена на момент старта процесса, независимо от того, сколько прошло времени».

**Чинить (минимально):**
1. заменить условие на `!_enteredThisSession && !_exitedThisSession` — после выхода не входить до следующей сессии (совпадает с правилом стратегии и с фиксом A1);
2. если повторный вход всё же нужен — входить по **текущей** цене (`minute.Open`), а не по `_sessionBar.Open`;
3. вход в сессии разрешать только в окне первых минут после 10:00, а при активации в середине дня — ждать следующую сессию. Иначе advisory-цена систематически неисполнима.

### 3.2 🟠 B2. Упавший движок никогда не перезапускается

**Файл:** `EngineSupervisor.cs:148–166`, `InstrumentEngine.cs:84`.

`InstrumentEngine.IsRunning` определён, но **нигде не используется**. Супервизор каждые 60 с сравнивает только идентификатор инструмента:

```csharp

{
    if (engine.TinkoffInstrumentId == (instrument.Uid ?? instrument.Figi))
    {
        continue;   // движок «на месте» — даже если его Task давно завершился
```

Между тем `StartCoreAsync` завершается штатно при:
* пустом `TinkoffInstrumentId` — `return` на строке 162;
* любом исключении в `WarmUpAndRestoreAsync` (например, RPC-ошибка T-Bank на старте) — `catch` на строке 210.

После этого инструмент **навсегда** перестаёт торговать: статус в метриках станет `stopped`/`error`, но никакого автоподъёма нет. Для системы, которая должна пережить ночь без оператора, это критично.

**Чинить:** в `SyncInstrumentsAsync` условие `continue` дополнить `&& engine.IsRunning`; упавшие движки останавливать и пересоздавать, с ограничением частоты рестартов и заметным ERROR-логом.

### 3.3 🟠 B3. Гонка при запуске воркера мультиплексора

**Файл:** `TinkoffMarketDataGateway.cs:110–121`.

```csharp
private void EnsureWorkerRunning()
{
    if (_worker is not null && !_worker.IsCompleted) return;
    _workerCts?.Dispose();
    _workerCts = new CancellationTokenSource();
    _worker = Task.Run(() => RunWorkerAsync(ct), ct);
}
```

Метод не синхронизирован, а вызывается из `SubscribeAsync` каждого движка — то есть из 39 параллельных задач, которые супервизор стартует одной пачкой (`EngineSupervisor.cs:180–183` → `engine.Start()` → fire-and-forget `StartCoreAsync`). Два потока могут одновременно увидеть «воркера нет» и поднять **два стрима**.

Последствия: (а) каждая свеча уедет в канал дважды → удвоение объёма, двойные проверки SL/TP, лишние обращения к БД; (б) нарушается `SingleWriter = true` (`:63`), заявленный при создании канала; (в) `_workerCts?.Dispose()` может освободить токен, с которым работает живой воркер.

**Чинить:** `lock (_gate)` вокруг тела `EnsureWorkerRunning` (или `SemaphoreSlim`), `_worker`/`_workerCts` — только под этим замком.

### 3.4 🟠 B4. Закрытие позиции не транзакционно

**Файл:** `InstrumentEngine.cs:433–465`.

```csharp
await _signalLogs.AddAsync(...);     // 1 контекст
await _tradeLogs.AddAsync(...);      // 2 контекст
await _positions.DeleteAsync(...);   // 3 контекст
```

Каждый репозиторий создаёт свой `DbContext` (`EfRepositories.cs`), общей транзакции нет. Если процесс умрёт между шагами 2 и 3, при рестарте `WarmUpAndRestoreAsync` (`InstrumentEngine.cs:266–283`) увидит: реализованный PnL **уже включает** закрытую сделку И открытую позицию в `OpenPositions` → cash пересчитается неверно, а движок будет «сторожить» уже закрытую позицию.

Симметрично на открытии (`InstrumentEngine.cs:348–357`): позиция сначала появляется в памяти, потом сохраняется. Исключение в `SaveAsync` → в памяти позиция есть, в БД нет, сигнал в Telegram ушёл.

**Чинить:** единый `UnitOfWork`/транзакция на «закрыть сделку» и «открыть сделку» (один `DbContext`, `SaveChanges` один раз). Отправку в Telegram — **после** успешного коммита, желательно через outbox.

Там же: на `OpenPositions.InstrumentId` нет уникального индекса (`AppDbContext.cs:36–46`), хотя инвариант «одна позиция на инструмент» — краеугольный. Уникальный индекс дешевле любой проверки в коде.

### 3.5 🟠 B5. «Сегодня» вычисляется один раз за жизнь процесса

**Файл:** `TinkoffMappers.cs:13–14`, используется в `TinkoffHistoricDailyBarsProvider.cs:32`.

```csharp
public static readonly DateTimeOffset TodayMoscowStart =
    new DateTimeOffset(DateTimeOffset.UtcNow.UtcDateTime.Date, TimeSpan.Zero).ToOffset(MoscowClock.Offset);
```

`static readonly` инициализируется при первом обращении к типу и больше не меняется. Сервис рассчитан на месяцы аптайма (`DEPLOYMENT.md`: «Restarts are expensive… Prefer Pause/Resume»). Через 30 дней работы любой `Resume`/пересоздание движка запросит историю с `To` = дате **месячной давности** → прогрев пройдёт на устаревших барах, ROC и ATR будут посчитаны по старым данным, и первый же сигнал будет неверным.

Плюс сама формула: полночь **UTC**, переведённая в +03:00, — это 03:00 МСК, а не начало московских суток. Имя вводит в заблуждение, и между 00:00 и 03:00 МСК дата «уезжает» на сутки назад.

**Чинить:** сделать вычисление методом (`static DateTimeOffset TodayMoscowStart() => ...`) и считать от московской даты: `DateOnly.FromDateTime(DateTimeOffset.UtcNow.ToOffset(MoscowClock.Offset).DateTime)`.

### 3.6 🟡 B6–B12. Средний уровень

**B6. Подписка пересобирается только при входящем сообщении.** `TinkoffMarketDataGateway.cs:143–154`: флаг `_restartRequested` проверяется внутри `await foreach` по ответам стрима. Если рынок закрыт или все подписанные инструменты молчат, свежедобавленный инструмент не попадёт в подписку до первой чужой свечи. **Чинить:** связанный `CancellationTokenSource`, отменяемый в `RequestRestart()`, — тогда чтение стрима прервётся сразу.

Там же (`:167–176`): при штатном EOF `delay` каждый раз сбрасывается в `_reconnectStart`, экспоненциальный бэкофф в этой ветке не работает. И ответы `SubscribeCandlesResponse` не инспектируются — неуспешная подписка на инструмент (делистинг, нет прав) молча выглядит как «тишина».

**B7. Первый день после старта — обрезанный дневной бар.** `InstrumentEngine.cs:318–331`: `_sessionDate` изначально `default`, поэтому первая же минутка открывает «сессию» с `Open/High/Low` этой минуты. Когда наступит следующий день, этот **неполный** бар уйдёт в `FinalizeDay` → в `OnBarCompleted` → в ATR (через `High−Low`) и в окно ROC наравне с полноценными. Плюс: если warm-up история уже содержит бар за сегодня, получится **два бара за одну дату** и окно ROC сместится. **Чинить:** помечать сессию как частичную (поле `Candle.IsComplete` для этого и заведено, но нигде не используется) и не подавать её в индикаторы; либо подтягивать дневной бар из истории.

**B8. Гонки чтения состояния.** `GetSnapshot()`, `CurrentSessionBar`, `Cash`, `Position` читаются из HTTP-обработчиков параллельно с `ProcessMinuteAsync`, без синхронизации. `_dailyBars` защищён `_barsLock`, а `_sessionBar` (это `Candle?` — структура из 7 полей) — нет: возможно чтение «полуобновлённого» значения. Для advisory-панели не смертельно, но список открытых позиций и equity могут показать несогласованный срез. **Чинить:** один `lock` на мутацию/чтение состояния движка или неизменяемый снимок, публикуемый через `Volatile.Write`.

**B9. Расхождение методики live vs research.** Бэктест проверяет SL/TP **только на дневных барах и только начиная со следующего дня после входа**; live-движок (`InstrumentEngine.cs:366–373`) проверяет их на каждой минутке. В `README.md` это названо «strictly more risk-reducing» — это неверно: интрадей-тейк закрывает прибыльную позицию раньше, а интрадей-стоп режет позиции, которые в бэктесте дожили бы до прибыли. Распределение сделок будет систематически иным, и сравнивать live-результат с отчётом будет некорректно. Правильная формулировка — «модель исполнения отличается; ожидаемое расхождение не оценено». Лучше — оценить: прогнать бэктест на минутках и сравнить.

**B10. `/api/equity-data` — квадратичный и с путаницей часовых поясов.** `AdminEndpoints.cs:130–160, 197–204`: `RealizedUpTo(day)` — полный проход по всем сделкам для **каждого** дня, `UnrealizedOn(day)` — проход по всем сделкам каждого тикера для каждого дня. При 40 инструментах × 700 дней × нескольких тысячах сделок это секунды CPU на запрос. Одного префиксного прохода достаточно: O(дни + сделки).

Там же даты ключуются как `DateTimeOffset.DateTime.Date`: у свечей из T-Bank смещение московское → получается московская дата, у сделок из PostgreSQL (`timestamptz` → offset 0) → **UTC-дата**. Для баров MOEX это почти всегда совпадает, но на вечерних/выходных аномалиях (о которых сам `AGENTS.md` предупреждает) даст расхождение. Использовать `MoscowClock.ToMoscowDate()` везде.

Мелочь: `pool = all.Count * InitialCapital` считает **все** инструменты, включая `Paused` и неразрешённые — знаменатель доходности растёт при простом добавлении тикера в список.

**B11. Удаление инструмента оставляет сирот.** `AdminEndpoints.cs:463–476` удаляет только строку `Instruments`. `TradeLogs`, `SignalLogs`, `OpenPositions` остаются: `/api/signals` продолжает их показывать, а `/api/equity-data` и `GET /` берут `tradeLogs.GetAllAsync()` / `SumAllRealizedPnlAsync()` → PnL удалённого инструмента навсегда сидит в equity пула. **Чинить:** каскадное удаление или явный soft-delete + фильтрация в агрегатах.

**B12. Безопасность.**
* `BasicAuthMiddleware.cs:66–69`: при **пустом** настроенном пароле `SafeEquals("", "")` возвращает `true` → вход с любым пустым паролем. Пустой пароль должен означать «запретить всё».
* `appsettings.json` содержит боевые дефолты `admin/admin` и `Password=root` в строке подключения. Даже как заглушки они опасны: `DEPLOYMENT.md` предлагает переопределять переменными окружения, но забытый override = открытая админка.

При этом `DEPLOYMENT.md` §8 пишет «do not expose it raw to the internet» и тут же даёт `sudo ufw allow 5080/tcp`, что как раз и открывает порт наружу. * **Нет ретраев/алертов при сбое Telegram.** `TelegramGateway.cs:44–52` глотает исключение, `InstrumentEngine.cs:420–427` глотает ещё раз (второй `catch` фактически мёртв). Не доставленный сигнал = пропущенная сделка у оператора; узнать об этом можно только из лога. Нужен outbox с ретраями и счётчик недоставленных в метриках.
* **Минимал-API: обязательные query-параметры.** `AdminEndpoints.cs:335` (`int limit`) и `:344` (`int page, int pageSize`) — не-nullable значимые типы без значения по умолчанию: при отсутствии параметра ASP.NET вернёт **400**, а `README.md` обещает «default 100» / «pageSize default 50». UI всегда их передаёт, поэтому баг виден только внешним потребителям API. Исправляется на `int? limit = null`.
* **`GetPageAsync`** (`EfRepositories.cs:236–245`) сортирует только по `Timestamp` без тай-брейкера — при одинаковых метках строки могут дублироваться/пропадать между страницами. Добавить `.ThenBy(x => x.Id)`.
* **`FindByTickerAsync`** (`EfRepositories.cs:43–47`) вызывает `ticker.ToUpperInvariant()` **внутри** выражения — лучше вычислить до запроса, чтобы не зависеть от трансляции.
* **`TinkoffTickerResolver.cs:34, 53, 60, 74`** — сбитые отступы (строки начинаются с нулевой колонки). Сборка не ругается, но стоит прогнать `dotnet format`.
* **`DbInitializer` сеет POLY** (делистинг 09.2024) — резолв будет падать или отдавать мёртвый инструмент.
* **Документация.** `AGENTS.md` описывает `TinkoffMarketDataMultiplexer` как отдельный компонент, а живёт он в файле `TinkoffMarketDataGateway.cs` — имя файла стоит привести в соответствие. `README.md` говорит «seeds the 39 research-basket tickers», и это верно, но `universe.py` — 40 имён (40-е — IMOEX, индекс); расхождение стоит проговорить явно.
* **Нет `Directory.Build.props`** с `TreatWarningsAsErrors`, `EnableNETAnalyzers`, `AnalysisLevel`. «0 warnings» сейчас — это ноль предупреждений при настройках по умолчанию.

### 3.8 Тесты

37 тестов (`AtrTests`, `RocSignalTests`, `EntryAndSizingTests`, `ExitTests`, `CashAndEquityTests`, `StateFlowTests`) покрывают доменную математику аккуратно и по делу: сидирование ATR как в pandas `ewm(adjust=False)`, окно ROC, приоритет SL над TP, выход **по уровню**, а не по экстремуму бара, механика cash для лонга и шорта, консистентность `WarmUp` и `FinalizeDay`. Это сильная сторона проекта.

Чего нет — ровно там, где находятся все найденные баги:

1. **`InstrumentEngine` не покрыт вообще.** Нужны тесты на фейковых `IMarketDataGateway`/репозиториях: агрегация сессии, переход через полночь, повторный вход после интрадей-выхода (B1), восстановление cash после рестарта (лонг и шорт), поведение при неполном первом баре (B7).
2. **`EngineSupervisor` не покрыт** — в частности, перезапуск упавшего движка (B2).
3. **`TinkoffMarketDataMultiplexer` не покрыт** — гонка при старте (B3), пересборка подписки (B6).
4. **Нет golden-теста паритета с Python.** Самый ценный из недостающих: прогнать `SBER.csv` через `MomentumEngineState` дневными барами и сверить список сделок с `Simulator` из `strategy_research.py` (фикстура — CSV с ожидаемыми сделками). Именно он бы поймал A1/B1 как расхождение «одна и та же цена входа у двух разных позиций».

## 4. Что сделано хорошо

* **Архитектура C#** — честная гексагональная: `Domain` без зависимостей, порты в `Application`, адаптеры в `Infrastructure`, хост в `Api`. Заменить T-Bank на другого брокера можно, не трогая стратегию.
* **`MomentumEngineState`** — корректный инкрементальный порт симулятора: сидирование ATR один в один с `pandas.ewm(adjust=False)`, скользящее окно ROC на `LinkedList` за O(1), явно задокументированные инварианты в XML-комментариях.
* **Восстановление cash после рестарта** (`InstrumentEngine.cs:266–283`) — тонкое место (учёт «зафиксированной» стоимости входа со знаком направления) сделано правильно и с объяснением в комментарии.
* **Мультиплексор одного gRPC-стрима** — верное решение реальной проблемы (лимит 32 стримов, ошибка 80001), с сохранением каналов между переподключениями.
* **Дисциплина документации**: `README`/`TECHNICAL`/`AGENTS`/`ADMIN`/`DEPLOYMENT` разделены по аудиториям, в `TECHNICAL.md` §3 прямо перечислены ранее исправленные баги («не сломайте снова»), а в `report.md` §9 честно перечислены несмоделированные издержки. Это редкая и правильная культура.
* **Отчёт генерируется из живых чисел**, а не набивается руками — MD и HTML строятся из одних и тех же данных.
* **Прогрев OOS-сигнала реальной пред-фолдовой историей** (`strategy_research.py:949`) — сделано аккуратно и с комментарием, почему это не look-ahead.
* **Basic-auth с постоянным временем сравнения**, отсутствие логирования секретов, `esc()` во всём `admin.html` — базовая гигиена соблюдена.

## 6. Одним абзацем

Инженерно проект сделан добротно: чистая архитектура, тесты на доменную математику, честный runbook и редкая привычка перечислять собственные ограничения. Но исследовательский слой содержит дефект модели исполнения — повторный вход по цене открытия бара, на котором позиция уже закрылась, — который даёт 69% сделок и ~80% всей заявленной прибыли; при корректной модели результат по проверенной выборке падает с +225% до +42% за 9,5 лет, и часть бумаг уходит в минус. Тот же дефект дословно перенесён в боевой сервис, где он приводит к публикации неисполнимых цен входа и неверных уровней SL/TP. Плюс к этому просадка пула занижена (считается только по реализованному PnL), дивидендные гэпы не учтены (и именно они «кормят» шорт-ногу), а кэш прогонов не инвалидируется, из-за чего документированный сценарий обновления данных молча возвращает старый отчёт. Первый этап работ — восстановить достоверность цифр; всё остальное имеет смысл только после этого.
